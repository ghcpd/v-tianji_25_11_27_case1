## Documentation vs. Implementation Mismatch Analysis

### Summary
Comparing README.md with the TypeScript sources reveals multiple discrepancies in defaults, return shapes, supported options, and validation rules. Below, each mismatch is documented with evidence and impact.

### ApiClient

#### 1) Timeout default
- **Doc (README.md › ApiClient constructor):** `timeout` default **5000 ms**
- **Code (ApiClient.ts):** `timeout` default **30000 ms**
- **Evidence**
  ```ts
  constructor(baseUrl: string, config = {}) {
    this.baseUrl = baseUrl;
    this.timeout = config.timeout ?? 30000;
  }
  ```
- **Impact:** Longer-than-documented waits; caller-side timeouts or UX expectations may be off by 6×.

#### 2) Headers config ignored
- **Doc:** `config.headers` sets default headers
- **Code:** `headers` parameter is accepted but never stored or used
- **Evidence**
  ```ts
  constructor(baseUrl: string, config = {}) {
    this.baseUrl = baseUrl;
    this.timeout = config.timeout ?? 30000;
    // no headers handling
  }
  ```
- **Impact:** Default headers (e.g., auth) aren’t applied; requests may lack required headers.

#### 3) GET/POST return shape
- **Doc:** Methods return **response data object** (examples show `{results: [...]}`)
- **Code:** Returns object wrapper `{ data: {...}, status, headers }`
- **Evidence**
  ```ts
  async get(...) {
    return { data: { results: [] }, status: 200, headers: {} };
  }
  async post(...) {
    return { data: { id: 1, ...body }, status: 201, headers: {} };
  }
  ```
- **Impact:** Consumers accessing `result.results` will get `undefined` (should use `result.data.results`).

#### 4) POST options/headers handling
- **Doc:** `post(endpoint, body, { headers })`
- **Code:** Ignores `options.headers`; also treats `body.headers` as `options`
- **Evidence**
  ```ts
  if (typeof body === 'object' && body.headers) {
    options = body;
    body = {};
  }
  // options.headers unused
  ```
- **Impact:** Headers aren’t applied; passing a body containing `headers` silently discards payload.

#### 5) DELETE return type
- **Doc:** `Promise<void>`
- **Code:** Returns `{ success: true, deletedId: ... }`
- **Evidence**
  ```ts
  async delete(endpoint: string): Promise<void> {
    return { success: true, deletedId: endpoint.split('/').pop() } as any;
  }
  ```
- **Impact:** Callers expecting void may ignore useful info; doc/code inconsistency.

#### 6) No real HTTP calls
- **Doc:** “HTTP client for making API requests”
- **Code:** Purely simulated responses; no fetch/axios/requests
- **Evidence:** Entire file contains only static return objects; no network API usage.
- **Impact:** Integrations will not hit real endpoints; docs overpromise capabilities.

### DataProcessor

#### 1) Default `limit`
- **Doc:** Default **unlimited**
- **Code:** Default **10**
- **Evidence**
  ```ts
  const limit = options.limit !== undefined ? options.limit : 10;
  return result.slice(0, limit);
  ```
- **Impact:** Results unexpectedly truncated.

#### 2) Sorting default
- **Doc:** `sort` default **false**; `sortBy` required only if `sort` is true
- **Code:** Automatically sorts when `sortBy` is provided (even if `sort` is unset)
- **Evidence**
  ```ts

  ```
- **Impact:** Ordering changes when merely supplying `sortBy`; potential perf cost and behavioral surprises.

#### 3) `validate` return type
- **Doc:** Returns **boolean**
- **Code:** Returns `{ valid: boolean, errors: string[] }`
- **Evidence**
  ```ts

    return { valid: ..., errors: ... } as any;
  }
  ```
- **Impact:** Type mismatch can break callers expecting a boolean; docs mislead about structure.

#### 4) Duplicate removal in `merge`
- **Doc:** Merges arrays **with duplicates removed**
- **Code:** Simply flattens and returns all items
- **Evidence**
  ```ts
  const merged = arraysToMerge.flat();
  return merged;
  ```

- **Impact:** Duplicate entries persist; downstream logic may misbehave.

### ValidationUtils

#### 1) `isValidEmail` return type
- **Doc:** Returns **boolean**
- **Code:** Returns object `{ valid, message, email }`
- **Evidence**
  ```ts
  return { valid: isValid, message: ..., email } as any;
  ```
- **Impact:** Boolean checks fail; docs misrepresent API shape.

#### 2) `isValidPhone` format handling
- **Doc:** Supports `'US'` or `'International'`; default `'US'`
- **Code:** Ignores `format`; always uses a permissive US regex
- **Evidence**
  ```ts
  export function isValidPhone(phone: string, format: 'US' | 'International' = 'US'): boolean {
    const usRegex = /^[\\d\\-\\(\\)\\s]+$/;
    return usRegex.test(phone);
  }
  ```
- **Impact:** International numbers may be rejected; callers can’t rely on `format`.

#### 3) `isValidUrl` scope
- **Doc:** Only **absolute** URLs (`http://` or `https://`)
- **Code:** Accepts relative paths and `localhost`
- **Evidence**
  ```ts
  if (url.startsWith('/') || url.startsWith('./')) return true;
  if (url.includes('localhost')) return true;
  new URL(url); return true;
  ```
- **Impact:** Relative/localhost URLs pass validation; possible security/validation gaps.

#### 4) `isValidDate` format
- **Doc:** Only ISO (`YYYY-MM-DD`)
- **Code:** Accepts ISO **or** US (`MM/DD/YYYY`) **or** EU (`DD.MM.YYYY`)
- **Evidence**
  ```ts
  return isoRegex.test(date) || usRegex.test(date) || euRegex.test(date);
  ```
- **Impact:** Broader acceptance than documented; ambiguity in date interpretation.
